## Summary of Issues Encountered

While building your **LangGraph tool-calling workflow**, you encountered several issues. They were mainly related to state structure, `tools_condition`, message history, environment configuration, and tool integration.

### 1. Incorrect graph routing

Initially, you had:

```python
graph.add_edge(START, "get_message")
graph.add_edge(START, "tools_node")
graph.add_edge("tools_node", START)
graph.add_edge("get_message", END)
```

The problem was that the graph was not using the normal **LLM → tool decision → tool → LLM** flow.

The correct pattern is:

```text
START
  ↓
LLM
  ↓
tools_condition
  ├── tools → ToolNode
  │             ↓
  │            LLM
  │
  └── END
```

---

### 2. `tools_condition` returned `"tools"` but no `"tools"` node existed

You had:

```python
graph.add_conditional_edges(
    "get_message",
    tools_condition
)
```

but your node was named:

```python
"tool_node"
```

`tools_condition` returns:

```text
"tools"
```

when the LLM requests a tool.

Therefore, LangGraph complained:

```text
ValueError:
At 'get_message' node, 'tools_condition' branch found unknown target 'tools'
```

You fixed this by explicitly mapping:

```python
graph.add_conditional_edges(
    "get_message",
    tools_condition,
    {
        "tools": "tool_node",
        "__end__": END,
    },
)
```

The mapping means:

```text
tools_condition returns "tools"
              ↓
        go to "tool_node"
```

---

### 3. `tools_condition` could not find your messages

You were using custom state such as:

```python
class ChatState(TypedDict):
    msg: ...
```

but `tools_condition` looks for:

```python
state["messages"]
```

by default.

This produced:

```text
ValueError: No messages found in input state to tool_edge
```

You had state like:

```python
{
    "msg": [...]
}
```

while `tools_condition` expected:

```python
{
    "messages": [...]
}
```

---

### 4. You wanted to use custom state instead of `MessagesState`

That's completely valid.

You can define:

```python
class ChatState(TypedDict):
    messages: list[BaseMessage]
```

You don't have to use `MessagesState`.

However, if you use the default `tools_condition`, the field needs to be called `messages`.

Alternatively, if you want to keep the field name `msg`, you can explicitly tell `tools_condition`:

```python
lambda state: tools_condition(
    state,
    messages_key="msg"
)
```

So:

```text
MessagesState
    ↓
predefined state

Custom ChatState
    ↓
you define the state yourself
```

---

### 5. You were invoking the graph with the wrong key

You had:

```python
workflow.invoke({
    "msg": ["what is the center of india?"]
})
```

while your graph was configured around:

```python
messages
```

The correct invocation is:

```python
workflow.invoke({
    "messages": [
        HumanMessage(content="what is the center of india?")
    ]
})
```

If you deliberately use `msg`, then your entire graph must consistently use `msg`, including `tools_condition(messages_key="msg")`.

---

### 6. `HumanMessage` should be constructed correctly

Instead of:

```python
HumanMessage("what is 1+22")
```

prefer:

```python
HumanMessage(content="what is 1+22")
```

So:

```python
workflow.invoke({
    "messages": [
        HumanMessage(content="what is 1+22")
    ]
})
```

### 7. The major tool-calling error: losing message history

Your latest error was:

```text
BadRequestError: Invalid parameter:
messages with role 'tool' must be a response
to a preceding message with 'tool_calls'.
```

This was the most important issue.

Your LLM/tool workflow needs to preserve this sequence:

```text
HumanMessage
     ↓
AIMessage(tool_calls=[...])
     ↓
ToolMessage(...)
     ↓
AIMessage(...)
```

But your state was effectively replacing the message history:

```python
return {
    "messages": [res]
}
```

Without a reducer, LangGraph treats this as:

```text
OLD messages
     ↓
REPLACE
     ↓
[new message]
```

That can cause the `ToolMessage` to reach the LLM without the preceding `AIMessage(tool_calls=...)`.

---

### 8. `add_messages` solves the history problem

For a custom state, you should use:

```python
from typing import Annotated
from langgraph.graph.message import add_messages

class ChatState(TypedDict):
    messages: Annotated[list[BaseMessage], add_messages]
```

Now:

```python
return {
    "messages": [res]
}
```

means:

```text
ADD this message to the existing history
```

rather than:

```text
REPLACE the entire history
```

So the tool loop maintains:

```text
[
    HumanMessage,
    AIMessage(tool_calls),
    ToolMessage,
    AIMessage
]
```

---

### 9. Tool binding is required for the LLM to request tools

You also asked whether tools need to be bound to the LLM.

For the LLM to decide and generate a tool call, you need something like:

```python
llm_with_tools = llm.bind_tools(tools)
```

Then:

```python
response = llm_with_tools.invoke(state["messages"])
```

The important distinction is:

```text
bind_tools()
    ↓
LLM knows which tools it can request

ToolNode(tools)
    ↓
actually executes those tools
```

Both parts are needed in the normal LangGraph tool-calling pattern.

### 10. LangSmith project name wasn't changing

You changed:

```python
os.environ["LANGSMITH_PROJECT"] = "abc"
```

but LangSmith continued showing the old project.

The likely causes were:

- Existing objects were created before the environment variable changed.
- The notebook had stale state.
- `LANGCHAIN_PROJECT` was also configured.
- `.env` contained the old project name.
- The graph/LLM had already been initialized.

For a notebook, set the environment variables **before creating your LLM/graph**, then recreate/compile them:

```python
os.environ["LANGSMITH_TRACING"] = "true"
os.environ["LANGSMITH_PROJECT"] = "abc"
```

and, if relevant:

```python
os.environ["LANGCHAIN_PROJECT"] = "abc"
```

## The final architecture you were working toward

Your custom-state version should conceptually look like:

```text
                    ┌──────────────┐
                    │   START      │
                    └──────┬───────┘
                           ↓
                    ┌──────────────┐
                    │  get_message │
                    │     (LLM)    │
                    └──────┬───────┘
                           ↓
                  ┌─────────────────┐
                  │ tools_condition │
                  └───────┬─────────┘
                     ┌────┴────┐
                     ↓         ↓
                  "tools"    "__end__"
                     ↓         ↓
                ┌─────────┐   END
                │ToolNode │
                └────┬────┘
                     ↓
                get_message
```

And your state should preserve the conversation:

```python
class ChatState(TypedDict):
    messages: Annotated[list[BaseMessage], add_messages]
```

### The three biggest lessons

1. **`tools_condition` needs access to the message history.**
2. **The LLM must be bound to the tools, while `ToolNode` executes them.**
3. **Tool-calling requires preserving the complete message sequence**, especially the `AIMessage(tool_calls)` immediately before the `ToolMessage`.

Those three concepts are the core of what was going wrong in your LangGraph workflow.
