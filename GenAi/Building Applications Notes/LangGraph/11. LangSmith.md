
# Module 1: The Core Problem & The Need for LangSmith

### 1. Detailed Explanation

In traditional software development, if you pass a specific input, you get a highly predictable output (deterministic behavior). If there is an error, the system throws a stack trace, pointing you directly to the line of code that failed.

However, LLMs are **non-deterministic** and **probabilistic**. The same prompt can yield different outputs, and a tiny tweak in your wording can alter your entire system's behavior. When something goes wrong in production—such as sudden slowness, unexpected billing spikes, or factually wrong answers (hallucinations)—the system usually does not crash. It runs successfully but returns a bad user experience. Without inside visibility, debugging these multi-stage "black box" workflows is nearly impossible.

---

### 2. Three Real-World Failure Scenarios

#### **Scenario A: The Job-Search Matcher (The Latency Nightmare)**

- **The App:** Students paste a Job Description (JD). The app scans their Google Drive portfolios, matches their skills, drafts a personalized cover letter, and proofreads it using several sequential LLM steps.
- **The Problem:** Normal execution takes 2 minutes. Suddenly, users complain it takes 7 to 10 minutes.
- **The Debugging Dilemma:** Since there are multiple backend components (PDF parsing, Drive scanning, skill matching, writing, and proofreading), the developer only sees the total elapsed time. Without a tool to inspect step-by-step latency, finding the culprit is incredibly difficult.

---

#### **Scenario B: The Solar Research Assistant (The Cost Spike)**

- **The App:** An autonomous agent that takes a research topic, scrapes papers from Google Scholar, extracts key metrics, and generates a unified report.
- **The Problem:** Average cost is 50 paise per report. Suddenly, some reports spike to ₹2 each, while others remain at 50 paise.
- **The Debugging Dilemma:** The agent was prompted to "loop and refine until a perfect report is created". For highly niche or complex topics, the agent got stuck in a loop of downloading papers, writing, and rejecting its own work. Because it did not throw an error, there was no traceback—only a massive invoice from OpenAI.

---

#### **Scenario C: The HR QA Chatbot (The Hallucination Crisis)**

- **The App:** A Retrieval-Augmented Generation (RAG) system answering policy questions (leave rules, insurance) for corporate freshers.
- **The Problem:** The bot tells an employee they can take a vacation to Goa whenever they want, leading them to leave without approval.
- **The Debugging Dilemma:** Why did the bot hallucinate?
    1. _Retriever Failure:_ Did the vector search fetch the wrong document (e.g., retrieving company history instead of the leave policy)?
    2. _Generator Failure:_ Did the LLM ignore the context because of a weak system prompt?

### 3. Defining Observability

**Observability** is the ability to understand a system's internal state simply by analyzing its external outputs, traces, and metrics. It converts a "black box" application into a "white box," letting you dissect execution step-by-step.

# Module 2: Core Architecture & Setup of LangSmith

### 1. The Core Concepts: Projects, Traces, and Runs

LangSmith structures your observability data into a clean, hierarchical tree:

|Concept|Definition|Analogous To|Example|
|:--|:--|:--|:--|
|**Project**|The overall container or workspace representing your application.|An entire codebase / repository.|`langsmith-demo` or `rag-chatbot`.|
|**Trace**|A single, end-to-end execution path of your application.|A single HTTP Request or User Query session.|A user asking: _"Who is the author of this book?"_|
|**Run**|An individual step or unit of work executed within a trace.|A specific function call or database query.|The Prompt Template, the LLM API call, or the Output Parser.|

---

### 2. Environmental Setup & Connection

To trace your application, you must configure your environment using specific variables. The system uses these keys to securely send telemetry data to the cloud dashboard:

- `LANGSMITH_TRACING=true`: Enables the tracing system globally.
- `LANGSMITH_ENDPOINT`: The API endpoint where traces are published.
- `LANGSMITH_API_KEY`: Your personal LangSmith access token.
- `LANGSMITH_PROJECT`: The specific project dashboard where your logs will group.

# Module 3: Basic Code Tracing: Simple Calls & Sequential Chains

### 1. Implicit Tracing (The LangChain Advantage)

If your application is built using standard LangChain components (using LangChain Expression Language or LCEL), **no code changes are required** to send logs to LangSmith. The framework automatically intercepts intermediate calls and forwards their metadata, tokens, and inputs/outputs to your dashboard.

---

### 2. Advanced Parameter Configuration

For clean debugging in production, you should enrich your traces with custom attributes:

- **Project Name Overriding:** You can change the target project within your script rather than using the `.env` file, allowing you to trace different files to different dashboards:
    
    ```
    os.environ["LANGCHAIN_PROJECT"] = "sequential-llm-app"
    ```
    
- **Custom Run Names:** Standard LCEL traces default to names like `RunnableSequence`. You can change this to a custom label like `"Sequential Chain"` using the `config` argument:
    
    ```
    chain.invoke({"topic": "AI"}, config={"run_name": "Sequential Chain"})
    ```
    
- **Metadata & Custom Tags:** To make your logs easily searchable under high volume, you can attach custom metadata (e.g., temperature values, parser types) and tags:
    
    ```
    config = {
        "tags": ["report-gen", "summary-v1"],
        "metadata": {
            "model_1_temp": 0.7,
            "parser_type": "StringOutputParser"
        }
    }
    ```

# Module 4: Tracing RAG Applications

### 1. The Challenges of Tracing RAG

A standard RAG app consists of setup steps (parsing a PDF, splitting text, building an index) and runtime steps (retrieving chunks, formatting, prompting, and generating a response).

By default, LangSmith **only traces LangChain runnables**. It does not log standard Python operations like file reading or manual list formatting. This creates a visibility gap where you cannot see if a slow-running pipeline is getting delayed during PDF parsing or embedding.

---

### 2. The `@traceable` Decorator

To trace any standard Python function (even if it does not use LangChain components), LangSmith provides the `@traceable` decorator. Wrapping your setup functions with this decorator ensures they appear in your trace timeline.

```
graph TD
    subgraph Raw Python Step (Tracked via @traceable)
        A[load_pdf] --> B[split_documents]
        B --> C[build_vector_store]
    end
    subgraph LCEL Pipeline (Tracked Automatically)
        C --> D[Retrieve Chunks]
        D --> E[Format Prompt]
        E --> F[ChatOpenAI Call]
    end
```

---

### 3. Performance Optimization (The Caching Strategy)

Running a full RAG app repeatedly can be highly inefficient if you re-load, re-split, and re-embed your documents on every execution.

To solve this, we implement local vector caching:

1. **First Run:** Check if a local index exists on disk. If not, execute the `@traceable` setup pipeline to load, split, and embed the PDF, then save the index locally.
2. **Subsequent Runs:** Load the index directly from disk. This cuts latency from ~30 seconds down to ~1.5 seconds.

# Module 5: Agentic and LangGraph Integrations

### 1. Tracing Autonomous ReAct Agents

Autonomous agents use a reasoning loop called **ReAct (Reasoning + Action)**. The agent evaluates the user prompt, determines if it needs a tool, executes that tool, reviews the output, and loops until it finds an answer.

In LangSmith, this appears as an structured execution tree:

- You can watch the agent initialize its execution state.
- You can track tool invocation inputs and outputs (including full JSON payloads from external APIs).
- You can see how past tool outputs feed back into the prompt for the next step, allowing you to trace the exact chain of thought.

---

### 2. LangGraph Integration

Because LangGraph and LangSmith are developed by the same team, they have a deep, native integration.

- **The Execution Mapping:** When you compile and run a graph, the entire run is logged as a single **Trace**.
- **Nodes as Runs:** Each **Node** in your graph is rendered as an independent **Run** in the LangSmith trace tree.
- **State Tracking:** Since LangGraph is stateful, LangSmith logs the exact state dictionary received and updated by every node, making it easy to see where data was corrupted.

# Module 6: Enterprise Features of LangSmith & LLMOps

LangSmith goes far beyond simple logging, offering a suite of production tools for managing your LLM application's lifecycle:


- **Monitoring & Alerting:** Monitors aggregate performance (average latency, error rates, token usage) across thousands of runs. You can configure custom rules to trigger alerts when metrics fall outside safe ranges.
- **Evaluation (LLM-as-a-Judge):** Helps you run test cases against "golden datasets" using metrics like faithfulness, relevance, and completeness. You can use a more powerful model (e.g., GPT-4) to evaluate and grade a smaller, cheaper production model.
- **Prompt Experimentation:** Provides a sandbox environment to run A/B tests on different prompts against a standard dataset to compare outputs side-by-step.
- **Dataset & Annotation Queues:** Allows you to capture real production traces and save them directly to datasets for fine-tuning or evaluation.
- **User Feedback Integration:** Tracks production feedback indicators (like thumbs-up/down) directly alongside the specific trace, helping you find and resolve user pain points.

# Final Revision Section

### 1. Key Takeaways

- **Non-Deterministic Behavior:** Standard trace debugging is vital because LLM-based apps rarely crash; they fail silently by generating incorrect outputs.
- **Zero-Config Tracing:** Simply adding the correct environment variables enables seamless LCEL step tracking.
- **Customization:** Use tags, custom run names, and metadata to make your production logs searchable.
- **`@traceable`:** Use this decorator to bring non-LangChain code into your trace hierarchy.
- **Nodes as Runs:** In LangGraph execution, nodes map to runs, allowing you to trace state changes across complex, looping graphs.

### 2. Important Terminology

- **Observability:** Understanding a system's internal states through external telemetry data.
- **ReAct Agent Loop:** An autonomous reasoning pattern involving alternating thoughts, actions, and observations.
- **RunnableParallel:** A LangChain component that runs multiple operations concurrently.
- **LLM-as-a-Judge:** Using a model to evaluate and score the output of another model.
- **LLMOps:** A set of operational practices for deploying, monitoring, and maintaining LLMs in production.

# Complete Python Implementation

This script demonstrates basic tracing, sequential prompting, and a database-cached RAG pipeline using `@traceable` annotations. It includes the API credentials provided in your configuration.

```
import os
import shutil
from typing import List, Dict, Any
from dotenv import load_dotenv

# =====================================================================
# 1. API KEY CONFIGURATIONS
# =====================================================================
os.environ["OPENAI_API_KEY"] = ''
os.environ["LANGCHAIN_TRACING_V2"] = "true"
os.environ["LANGCHAIN_ENDPOINT"] = 'https://api.smith.langchain.com'
os.environ["LANGCHAIN_API_KEY"] = ''
os.environ["LANGCHAIN_PROJECT"] = 'langsmith-demo'

# =====================================================================
# 2. REQUIRED IMPORTS
# =====================================================================
from langsmith import traceable
from langchain_openai import ChatOpenAI, OpenAIEmbeddings
from langchain_core.prompts import ChatPromptTemplate
from langchain_core.output_parsers import StrOutputParser
from langchain_core.runnables import RunnablePassthrough
from langchain_community.vectorstores import FAISS

# =====================================================================
# 3. COMPONENT 1: BASIC & SEQUENTIAL CHAIN TRACING
# =====================================================================

def execute_sequential_chain(topic: str):
    """
    Executes a two-stage sequential chain.
    First generates a detailed report, then condenses it into a summary.
    """
    # Overriding the default target project specifically for this execution run
    os.environ["LANGCHAIN_PROJECT"] = "sequential-llm-app"

    model_mini = ChatOpenAI(model="gpt-4o-mini", temperature=0.3)
    model_main = ChatOpenAI(model="gpt-4o", temperature=0.7)

    prompt_report = ChatPromptTemplate.from_template("Generate a brief overview report on: {topic}")
    prompt_summary = ChatPromptTemplate.from_template("Condense this report into 3 bullet points: {report}")

    # Building our chain using LangChain Expression Language (LCEL)
    chain = (
        {"report": prompt_report | model_mini | StrOutputParser()}
        | prompt_summary
        | model_main
        | StrOutputParser()
    )

    # Custom tracing metadata and tags configuration
    config = {
        "run_name": "Sequential Educational Report",
        "tags": ["prod-demo", "sequential-chain"],
        "metadata": {
            "developer": "Nitish",
            "environment": "Production-Test"
        }
    }

    print(f"\n--- Running Sequential Chain for Topic: '{topic}' ---")
    result = chain.invoke({"topic": topic}, config=config)
    print("Result Summary:\n", result)

# =====================================================================
# 4. COMPONENT 2: @traceable DECORATED RAG WITH FAISS INDEX CACHING
# =====================================================================

# Mock Data used to construct our PDF text context to keep execution simple
MOCK_BOOK_PAGES = [
    "Introduction to Statistical Learning. Page 1: Chapter 1 discusses linear regression models.",
    "Introduction to Statistical Learning. Page 2: Chapter 2 details classification with logistic regression.",
    "Introduction to Statistical Learning. Page 3: Authors of this textbook are Gareth James, Daniela Witten, Trevor Hastie and Robert Tibshirani."
]

@traceable(name="Mock Load Document")
def load_mock_pdf() -> List[str]:
    """Simulates loading pages from an external PDF document."""
    return MOCK_BOOK_PAGES

@traceable(name="Document Chunker")
def split_document_chunks(pages: List[str]) -> List[str]:
    """Splits raw text documents into processing chunks."""
    chunks = []
    for page in pages:
        chunks.extend([page[i:i+100] for i in range(0, len(page), 100)])
    return chunks

@traceable(name="Index Creator")
def create_faiss_vector_store(chunks: List[str], path: str) -> FAISS:
    """Generates embedding vectors and persists the database index to disk."""
    embeddings = OpenAIEmbeddings(model="text-embedding-3-small")
    db = FAISS.from_texts(chunks, embeddings)
    db.save_local(path)
    return db

@traceable(name="Master Setup Pipeline")
def setup_rag_retrieval_index(index_path: str) -> FAISS:
    """
    Coordinates loading, chunking, and embedding.
    Uses cached indices on subsequent executions to optimize performance.
    """
    if os.path.exists(index_path):
        print("[CACHE DETECTED] Loading vector index from local disk...")
        embeddings = OpenAIEmbeddings(model="text-embedding-3-small")
        return FAISS.load_local(index_path, embeddings, allow_dangerous_deserialization=True)

    print("[NO CACHE FOUND] Creating vector store indices from scratch...")
    raw_pages = load_mock_pdf()
    text_chunks = split_document_chunks(raw_pages)
    return create_faiss_vector_store(text_chunks, index_path)

def run_rag_query(query: str, index_path: str):
    """Executes vector retrieval and uses an LLM to answer the query."""
    os.environ["LANGCHAIN_PROJECT"] = "rag-chatbot-demo"

    db = setup_rag_retrieval_index(index_path)
    retriever = db.as_retriever(search_kwargs={"k": 2})

    prompt = ChatPromptTemplate.from_template(
        "Answer the question based strictly on the provided context.\n\nContext: {context}\n\nQuestion: {question}"
    )
    model = ChatOpenAI(model="gpt-4o-mini", temperature=0)

    def format_retrieved_docs(docs):
        return "\n\n".join(doc.page_content for doc in docs)

    rag_chain = (
        {"context": retriever | format_retrieved_docs, "question": RunnablePassthrough()}
        | prompt
        | model
        | StrOutputParser()
    )

    config = {
        "run_name": "RAG Query Evaluation",
        "tags": ["rag-v1"]
    }

    print(f"\n--- Running RAG Pipeline for query: '{query}' ---")
    answer = rag_chain.invoke(query, config=config)
    print("Answer: ", answer)

# =====================================================================
# 5. CODE EXECUTION GATEWAY
# =====================================================================
if __name__ == "__main__":
    INDEX_DIR = "./cached_faiss_index"

    # Cleanup any previous runs to ensure cache build tracing is clear
    if os.path.exists(INDEX_DIR):
        shutil.rmtree(INDEX_DIR)

    try:
        # Step A: Run basic sequential chain
        execute_sequential_chain(topic="Generative AI Observability")

        # Step B: Run RAG - First Run (Builds Cache)
        run_rag_query(query="Who are the authors of the book?", index_path=INDEX_DIR)

        # Step C: Run RAG - Second Run (Loads Cache Instantly)
        run_rag_query(query="What is discussed in chapter 1?", index_path=INDEX_DIR)

    except Exception as e:
        print(f"\nExecution error encountered: {e}")
```
