### **3. Tools in LangGraph**

#### **Detailed Notes**

To understand how tools integrate with LangGraph, let us examine the evolution of our system design:

#### **A. The Traditional Flow (Static & Linear)**

In a basic chatbot workflow, a user's question goes directly from the `START` block into a `Chat Node` (holding our LLM) and immediately exits at the `END` block. The flow is entirely linear and cannot detour.

```
graph LR
    START((START)) --> ChatNode[Chat Node: LLM]
    ChatNode --> END((END))
```

#### **B. The Agentic Flow (Dynamic & Cyclic)**

To enable tools, we must transform this linear architecture into a **looping graph**. The `Chat Node` no longer just answers questions; it acts as a **Decision-Maker (Router)**.

- If the user asks a normal question (e.g., _"How are you?"_), the LLM answers directly and routes the execution to `END`.
- If the user asks an action-oriented question (e.g., _"What is 245 * 123?"_), the LLM detects that it cannot answer accurately on its own. It selects the appropriate tool from its bound arsenal, packages the required parameters, and routes the execution to a specialized **ToolNode**.

#### **The Crucial Tool Loop Requirement**

A naive workflow might try to go from `Chat Node -> Tool Node -> END`. However, this creates two major limitations:

1. **Raw, Technical Outputs:** Tools return raw data payloads (like complex JSON structures from stock APIs). Displaying this directly to the user results in a poor user experience.
2. **No Multi-Step Reasoning:** The agent cannot use the output of Tool A to execute Tool B.

**The Solution:** We draw an edge from the **ToolNode back to the Chat Node**. When the Tool Node executes and updates the state with its raw output, the control goes back to the LLM. The LLM reviews the entire conversational history (including the tool's raw result) and either cleanly formats the final answer for the user or decides to run another tool.

![[Pasted image 20260908203236.png]]

```
graph TD
    START((START)) --> ChatNode[Chat Node: LLM with Bound Tools]
    ChatNode --> CondEdge{Tools Condition?}
    CondEdge -- "No Tools Needed" --> END((END))
    CondEdge -- "Tool Call Requested" --> ToolNode[Tool Node: Executes Tools]
    ToolNode --> ChatNode
```

### **4. Definition of ToolNode**

#### **Detailed Notes**

Managing, routing, and executing tools manually in code is repetitive and error-prone. LangGraph solves this by providing pre-built utility blocks to handle tool execution seamlessly.

#### **A. What is a `ToolNode`?**

In LangGraph, a **`ToolNode`** is a pre-built, ready-made node class (imported from `langgraph.prebuilt.ToolNode`) that acts as a bridge between your graph and your list of tools.

- **How it operates:** It listens for tool calls generated by the LLM, reads the arguments, automatically maps the request to the correct tool in your collection, executes it, and appends the result to the graph state.

#### **B. What is `tools_condition`?**

To decide whether the execution path should branch to the `ToolNode` or exit directly to the `END` block, we use a pre-built conditional edge router function called **`tools_condition`** (imported from `langgraph.prebuilt.tools_condition`).

- **How it operates:** It checks the last message in the graph's state. If the message contains a request to invoke tools (`tool_calls`), it routes the flow to the `ToolNode`. Otherwise, it routes the flow to `END`.

### **6. Final Changes & Streaming Optimization**

#### **Detailed Notes**

Once the backend agent loop is built, running it within a streaming user interface reveals an interesting UX bug: **the raw output from the tools streams directly onto the screen** alongside the final answer.

#### **The Cause**

Under the hood, the graph emits messages from both the **`ToolNode`** (which outputs `ToolMessage` payloads) and the **`Chat Node`** (which outputs `AIMessage` payloads). A naive frontend streaming loop treats all incoming packets equally, causing raw JSON strings to render on-screen before the polished AI response.

#### **The Solution: Type Filtering**

We resolve this by adding a type-check filter in the frontend rendering loop. The streaming engine is configured to inspect each incoming chunk and **only stream if the package is an instance of `AIMessage`**. This completely hides technical `ToolMessage` payloads from the UI while keeping the final, polished response intact.

```
flowchart TD
    A[Incoming Stream Chunk] --> B{Is chunk an AIMessage?}
    B -- "Yes" --> C[Stream Token to UI]
    B -- "No: ToolMessage" --> D[Ignore Token in UI]
```

#### **Status Containers for UX**

To keep the user informed during multi-step tool executions, we integrate Streamlit's **Status Container (`st.status`)**. This provides real-time updates of background actions (e.g., displaying _"Using DuckDuckGo Search..."_ or _"Calculating result..."_). This keeps the user engaged while the background tools are processing.

# Final Revision Section

### **Key Takeaways**

- **LLMs as Orchestrators:** In agentic workflows, the LLM does not execute actions; it decides _which_ tool to call and _how_ to parameterize it.
- **The Crucial Loop:** Routing tool outputs back to the LLM enables conversational formatting of technical payloads and multi-step reasoning chains.
- **Docstrings are Code:** Custom tools rely on descriptive Python docstrings. The LLM reads these docstrings to understand what a tool does and when to call it.
- **Pre-built Speed:** `ToolNode` and `tools_condition` eliminate the need to write custom routing boilerplate, streamlining tool integration in LangGraph.

### **Important Terminology**

- **`ToolNode`:** A pre-built LangGraph node that manages tool execution.
- **`tools_condition`:** A pre-built conditional edge router that branches flows based on tool requests.
- **`bind_tools`:** A LangChain method that registers a set of tools with an LLM instance.
- **`AIMessage`:** A message class representing the conversational output of the assistant.
- **`ToolMessage`:** A message class containing raw data returned by an executed tool.
