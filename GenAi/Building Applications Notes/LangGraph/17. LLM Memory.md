# 1. Introduction: Why Memory Matters in GenAI

### Detailed Explanation

Memory is a fundamental component of human cognition, and it is equally critical for Generative AI applications. Whether you are constructing a simple customer support chatbot or an autonomous multi-agent system, the application cannot function effectively without a mechanism to store, retrieve, and reference past interactions.

Without memory, an AI system treats every single user input in isolation. This creates a highly frustrating user experience where the user must continuously repeat context, preferences, and previously established facts.

```
graph TD
    A[User Request] --> B{AI System}
    B -- Without Memory --> C[Treats input as isolated turn -> Loss of Context]
    B -- With Memory --> D[References Conversation History & User Facts -> Contextual Response]
```

### Key Concepts

- **Generative AI Memory:** The mechanism by which an AI application retains information across user turns or across different sessions over time.
- **Framework-Agnostic Understanding:** Studying memory from first principles rather than relying on a single library (like LangChain or LlamaIndex) ensures you can design custom memory layers for any application architecture.

### Why It Matters

Building a GenAI application without memory severely degrades user experience. Understanding how memory is engineered allows developers to transition from basic single-prompt scripts to production-grade conversational agents and personal assistants.

### Examples

- **Source Example:** A chatbot attempting to assist a user with a multi-step troubleshooting task. Without memory, it forgets the user's operating system or problem description from the immediately preceding message.
- **Additional Example (Not From Source):** An AI medical assistant that forgets a patient's reported symptoms or drug allergies mid-conversation, forcing the patient to re-enter their medical history with every follow-up question.

### Key Takeaways

- Memory is a non-negotiable requirement for non-trivial GenAI applications.
- Memory is not built into LLM weights natively; it must be engineered around the model.

# 2. How LLMs Work at Inference (Stateless by Design)

### Detailed Explanation

To understand why LLMs lack memory, we must examine how an LLM operates at the time of prediction (inference) using a mathematical approach.

At inference time, a Large Language Model can be represented as a **parameterized mathematical function**:

\[y = f(x, \theta)\]

Where:

- \(f\): The complex mathematical transformer architecture.
- \(x\): The input tokens (the prompt provided by the user).
- \(\theta\): The model parameters (the weights learned during pre-training and fine-tuning).
- \(y\): The output tokens generated by the model.

```
flowchart LR
    X["Input Tokens (x)"] --> F["LLM Function f(x, θ)"]
    TH["Model Weights (θ) - Billions of Fixed Parameters"] --> F
    F --> Y["Output Tokens (y)"]
```

### Simple Explanation \(\rightarrow\) Intuitive Analogy \(\rightarrow\) Technical Explanation

- **Simple Explanation:** An LLM is like a massive mathematical calculator. You give it numbers (input tokens \(x\)), it uses internal formulas (\(\theta\)), and it outputs a result (\(y\)).
- **Intuitive Analogy (Linear Regression):** Consider a simple line equation \(y = mx + b\). Here, \(x\) is the input from the user, \(y\) is the predicted output, and \(m\) (slope) and \(b\) (intercept) are parameters learned from training data. Once \(m\) and \(b\) are calculated during training, they remain fixed during prediction. An LLM works the same way, except instead of two parameters (\(m\) and \(b\)), it has **billions of parameters (\(\theta\))**.
- **Technical Explanation:** During inference, the weights \(\theta\) are read-only and frozen. The output \(y\) depends strictly on the current input vector \(x\) and the frozen parameters \(\theta\). The model does not modify \(\theta\) when answering a user, nor does it save \(x\) or \(y\) inside its architecture.

### Concept Summary Table

|Mathematical Component|Real-World Representation|Mutability at Inference|User Control|
|:--|:--|:--|:--|
|\(x\)|Input Tokens / Prompt|Mutable per request|Full Control|
|\(\theta\)|Model Weights (Parameters)|Frozen / Fixed|No Control|
|\(y\)|Generated Output Tokens|Produced per request|Indirect via \(x\)|

### Key Takeaways

- LLM inference is purely a mathematical function call \(y = f(x, \theta)\).
- Parameters (\(\theta\)) are locked during inference; they do not store user session data.

# 3. The Core Problem: LLMs Have No Memory

### Detailed Explanation

Because an LLM at inference is a parameterized function \(y = f(x, \theta)\), it possesses a critical computer science property: **Statelessness**.

A system is **stateless** if its output depends **only** on the current input provided to it at that exact moment, completely independent of any prior inputs or outputs.

\[\text{Call 1: } y_1 = f(x_1, \theta)\] \[\text{Call 2: } y_2 = f(x_2, \theta)\]

In Call 2, \(y_2\) is calculated using \(x_2\) and \(\theta\). It has **zero awareness** of \(x_1\) or \(y_1\).

```
sequenceDiagram
    participant User
    participant LLM as LLM Function f(x, θ)
    User->>LLM: Call 1: x1 = "My name is Nitish"
    LLM-->>User: Output y1 = "Nice to meet you, Nitish!"
    User->>LLM: Call 2: x2 = "What is my name?"
    LLM-->>User: Output y2 = "I am sorry, I do not know your name."
```

### The GenAI Paradox / Deadlock

This creates a paradox in AI application engineering:

- **Fact 1:** LLMs are intrinsically stateless and have zero native memory.
- **Fact 2:** Virtually all real-world GenAI and Agentic AI applications require memory to function.
- **The Deadlock:** How do we build stateful, conversational AI applications on top of a fundamentally stateless mathematical engine?

```
graph LR
    F1[Fact 1: LLMs are inherently stateless] --- DL{THE DEADLOCK}
    F2[Fact 2: AI Apps require memory & context] --- DL
    DL --> SOL[Fact 3: Memory must be built as an external architecture around the LLM]
```

### Key Takeaways

- LLMs suffer from absolute statelessness at inference.
- Solving the deadlock requires building an **external memory system** wrapped around the LLM.

# 4. Building Memory Around LLMs (A First-Principles Approach)

### Detailed Explanation

Since the LLM cannot remember past inputs internally, the memory feature must be **invented externally**. Instead of attempting to modify the frozen model parameters (\(\theta\)), developers must manipulate the only variable they have full control over: **the input tokens (\(x\))**.

To build memory around an LLM from first principles, we must understand two fundamental properties of modern LLMs: **Context Windows** and **In-Context Learning**.

---

# 5. Foundational Pillars: Context Window and In-Context Learning

### Detailed Explanation

#### Pillar 1: The Context Window

The **Context Window** is the maximum amount of text (measured in tokens) that an LLM can read, process, and consider at one single time before generating an output.

- **Camera Lens Analogy:** Imagine an LLM as a camera and the context window as its lens. A small camera lens can only capture a narrow fragment of a landscape. A wide-angle lens captures the entire scene in a single shot. Similarly, a large context window allows the LLM to "see" a massive volume of text simultaneously.
- **Modern Scale:** Older models had context windows of 2,000 to 4,000 tokens. Modern models (e.g., GPT-4o, Claude 3.5) support 128,000 tokens (~200 pages of text), while models like Gemini support up to 1,000,000+ tokens (~1,500+ pages).

```
graph LR
    A[Small Context Window e.g. 2k Tokens] --> B[Can only process short prompts/snippets]
    C[Large Context Window e.g. 128k - 1M Tokens] --> D[Can process hundreds of document pages at once]
```

#### Pillar 2: In-Context Learning (ICL)

**In-Context Learning** is an emergent ability of Large Language Models where the model uses information, patterns, and instructions provided **directly inside the prompt (\(x\))** to answer questions, without relying solely on its pre-trained parametric knowledge (\(\theta\)).

- **Parametric Knowledge vs. In-Context Knowledge:**
    - _Parametric Knowledge:_ Information stored permanently in weights \(\theta\) during training.
    - _In-Context Knowledge:_ Temporary information supplied dynamically in prompt \(x\).

```
flowchart TD
    Prompt["Prompt (x) Contains Private 100-page PDF + Question"] --> LLM["LLM Function"]
    LLM --> Decision{"Answer in Parametric Knowledge (θ)?"}
    Decision -- No --> ICL["In-Context Learning Engine reads PDF in Prompt"]
    ICL --> Output["Accurate Answer generated from Prompt Context"]
```

### How They Combine to Enable Memory

By combining a **Large Context Window** (the capacity to pass massive token counts) with **In-Context Learning** (the ability to extract facts from the prompt), we can create the illusion of memory.

Instead of calling: \[y_2 = f(x_2, \theta)\]

We concatenate the entire conversation history into the new input: \[y_2 = f(\text{concat}(x_1, y_1, x_2), \theta)\]

```
flowchart LR
    X1["User: My name is Nitish (x1)"] --> Hist["Conversation Buffer [x1, y1]"]
    Y1["AI: Nice to meet you! (y1)"] --> Hist
    X2["User: What is my name? (x2)"] --> Concat["Concatenated Input: x1 + y1 + x2"]
    Hist --> Concat
    Concat --> LLM["LLM Inference Call"]
    LLM --> ICL["In-Context Learning reads x1 in prompt"]
    ICL --> Y2["AI: Your name is Nitish! (y2)"]
```

### Key Takeaways

- Memory is not magic; it is simply **passing conversation history back into \(x\) on every turn**.
- The LLM does not "remember" the past; it reads the past afresh on every API call via In-Context Learning.

# 6. Implementing Short-Term Memory Using Conversation History

### Detailed Explanation

To turn a stateless LLM into a stateful system, we maintain a dynamic array or list variable—often referred to as a **Conversation Buffer** or **State**.

### Step-by-Step Execution Mechanics

1. **Initialize Buffer:** Create a state variable (e.g., `messages = []`).
2. **User Turn 1:** Append user input \(x_1\) to `messages`.
3. **Invoke Model 1:** Pass `messages` (\([x_1]\)) to `llm.invoke()`.
4. **Append AI Response 1:** Receive output \(y_1\) and append it to `messages` (\([x_1, y_1]\)).
5. **User Turn 2:** Append new user question \(x_2\) to `messages` (\([x_1, y_1, x_2]\)).
6. **Invoke Model 2:** Pass the concatenated `messages` list to `llm.invoke()`.
7. **Result:** The LLM reads \(x_1\) and \(y_1\) via In-Context Learning and answers \(x_2\) accurately.

```
# Minimal Python Conceptual Implementation of Short-Term Memory
from langchain_openai import ChatOpenAI

model = ChatOpenAI(model="gpt-4o-mini")
messages = []

# Turn 1
x1 = "My name is Nitish"
messages.append({"role": "user", "content": x1})
y1 = model.invoke(messages).content
messages.append({"role": "assistant", "content": y1})

# Turn 2
x2 = "What is my name?"
messages.append({"role": "user", "content": x2})
y2 = model.invoke(messages).content

print(y2) # Output: Your name is Nitish.
```

### Key Takeaways

- The system state moves from the model weights (\(\theta\)) into the application script (`messages` buffer).
- Because this variable resides in volatile RAM, restarting the application erases the memory.

# 7. How Chatbots Implement Short-Term Memory (Thread Scoping)

### Detailed Explanation

In commercial applications (like ChatGPT, Claude, or Gemini), short-term memory is **not global** across the entire user account. It is strictly **Thread-Scoped** or **Conversation-Scoped**.

```
graph TD
    UserAccount[User Account] --> Thread1["Thread ID 1 (e.g. Python Script Help)"]
    UserAccount --> Thread2["Thread ID 2 (e.g. Travel Itinerary)"]

    Thread1 --> Buffer1["Conversation Buffer 1 [x1, y1, x2, y2]"]
    Thread2 --> Buffer2["Conversation Buffer 2 [x1, y1]"]

    Buffer1 -. Isolated from .- Buffer2
```

### Technical Terminology & Rules

- **Thread / Conversation:** A single, logically bounded session between a user and the AI.
- **Thread Scoping:** Short-Term Memory resides strictly inside one `thread_id`.
- **Isolation:** Messages from `Thread 1` are never concatenated into API calls for `Thread 2`. This prevents cross-topic confusion and saves token capacity.

---

# 8. Limitations of Short-Term Memory

While Short-Term Memory (STM) provides immediate conversational continuity, it suffers from **three severe architectural drawbacks**.

```
mindmap
  root((Short-Term Memory Limitations))
    Problem 1: Fragility
      Resides in volatile RAM
      Server crash / page refresh erases memory
      Requires Database Persistence
    Problem 2: Context Window Limits
      Long chats accumulate huge token counts
      Exceeds maximum token limits
      Causes hallucinations / crashes
    Problem 3: Thread Isolation
      No cross-thread continuity
      Forgets user preferences across chats
      Learning never compounds over time
```

---

### Problem 1: Fragility (Loss of Memory on Crash/Reset)

- **Detailed Notes:** Because standard STM resides in an in-memory variable (RAM), any server crash, deployment update, or browser refresh wipes the buffer.
- **Solution (Persistence Layer):** Connect the short-term memory buffer to a durable database (e.g., SQLite, PostgreSQL, Redis). Store every message under a unique `thread_id` so that reloading a session fetches historic messages back into the buffer.

---

### Problem 2: The Context Window Overflow Problem

- **Detailed Notes:** In long-running conversations (e.g., 500+ messages), concatenating the full history eventually exceeds the model's context window limit. This leads to severe performance degradation, hallucinations, or outright API errors.

```
flowchart LR
    A[Long Running Chat: 500 Messages] --> B[Tokenize Conversation History]
    B --> C{Token Count > Context Window?}
    C -- Yes --> D[LLM Degradation / Hallucination / Context Overflow Error]
    C -- No --> E[Normal Processing]
```

- **Solutions:**
    1. **Trimming:** Discard older messages and send only the most recent \(N\) messages (e.g., keep last 50 messages). _Drawback:_ Loses important context established early in the chat.
    2. **Summarization:** Pass older messages to a background LLM to generate a concise summary (e.g., _"User is building a React app with a SQL backend"_), then append the summary alongside the recent \(N\) messages.

```
graph TD
    OldMsgs[Messages 1 to 450] --> SummaryLLM[Background Summary LLM]
    SummaryLLM --> ConciseSummary[Concise Summary Text ~200 Tokens]
    RecentMsgs[Recent Messages 451 to 500] --> ActiveBuffer[Active Context Window]
    ConciseSummary --> ActiveBuffer
    ActiveBuffer --> FinalCall[LLM Call within Safe Token Limits]
```

### Problem 3: Thread Isolation (The "Stranger Danger" Problem)

- **Detailed Notes:** Because STM is strictly thread-scoped, opening a new chat window makes the user a total stranger to the AI once again.

#### The Three Negative Impacts of Thread Isolation

1. **No User Personalization Across Chats:** If a user states in Chat 1 that they are a Python developer who dislikes Java, starting Chat 2 results in the AI suggesting Java code again.
2. **Learning Never Compounds:** The AI cannot adapt or improve its behavior based on past interactions across different sessions.
3. **Cross-Thread Reasoning is Impossible:** The user cannot ask: _"What did we decide during our planning session yesterday?"_.

```
sequenceDiagram
    participant User
    participant Chat1 as Thread 1 (Yesterday)
    participant Chat2 as Thread 2 (Today)

    User->>Chat1: "I am a Python developer. Always give code in Python."
    Chat1-->>User: "Got it! I will use Python."

    User->>Chat2: "Write a script to parse a CSV file."
    Chat2-->>User: "Here is a Java solution..."
    Note over Chat2: Thread Isolation: Has zero awareness of Thread 1!
```

# 9. Why We Need Long-Term Memory

### Detailed Explanation

To overcome the limitations of short-term memory, we must engineer a **Long-Term Memory (LTM)** system.

Long-Term Memory must possess two core properties:

1. **Cross-Thread Persistence:** It must store special facts that survive beyond the boundary of a single thread or session.
2. **High Selectivity:** It must **not** store full raw chat transcripts blindly. It must extract, filter, and store only stable, reusable facts about the user and the system.

```
graph TD
    subgraph Short-Term Memory (STM)
        A[Thread Scoped]
        B[Stores Raw Message Transcripts]
        C[Erased / Cleared on New Chat]
    end

    subgraph Long-Term Memory (LTM)
        D[User / App Scoped]
        E[Extracts & Stores Selective Facts]
        F[Persists Permanently Across All Chats]
    end
```

# 10. The Three Types of Long-Term Memory (Episodic, Semantic, Procedural)

Long-Term Memory in GenAI is categorized into three distinct architectural layers inspired by cognitive science.

```
mindmap
  root((Long-Term Memory Types))
    Episodic Memory
      Past Events & Sequences
      What happened in prior sessions?
      e.g., 'User rejected Deployment Plan B'
    Semantic Memory
      Facts & Knowledge
      What is true about the User & System?
      e.g., 'User prefers Python', 'Budget = $10k'
    Procedural Memory
      Rules & Workflows
      How should tasks be executed?
      e.g., 'Avoid subqueries; use window functions'
```

### Concept Comparison Table

|Memory Type|Core Question Answered|Information Stored|Real-World Example|
|:--|:--|:--|:--|
|**Episodic Memory**|_What happened in the past?_|Specific past events, decisions, and execution outcomes.|"In the last session, deployment failed due to invalid AWS credentials."|
|**Semantic Memory**|_What is true about the user/system?_|Verified facts, identity, preferences, and system parameters.|"User is a male AI instructor named Nitish who prefers Python."|
|**Procedural Memory**|_How should tasks be executed?_|Rules, operational strategies, workflows, and learned behaviors.|"When generating SQL for this user, always use window functions instead of subqueries."|

# 11. How Long-Term Memory Works (High-Level 4-Step Architecture)

The high-level lifecycle of a Long-Term Memory system consists of four sequential stages:

```
flowchart TD
    Step1["1. CREATION / UPDATE<br>(Extract facts from chat)"] --> Step2["2. STORAGE<br>(Save to DB / Vector Store)"]
    Step2 --> Step3["3. RETRIEVAL<br>(Selective search for query)"]
    Step3 --> Step4["4. INJECTION<br>(Inject into STM / Context Window)"]
    Step4 --> LLM["LLM Inference Call"]
```


![[Pasted image 20260929014324.png]]

### Step 1: Creation & Extraction

During or immediately after a conversation turn, a background evaluator analyzes user messages, model outputs, and tool results. It strips out noise and extracts candidate memory facts (e.g., _"User prefers Python over Java"_). It also assigns scope (User-level vs. App-level).

### Step 2: Storage

The extracted facts are saved into a durable memory store. Depending on the memory type, storage layers include:

- _Relational Databases (SQL):_ For structured user profiles and preferences.
- _Key-Value Stores (Redis):_ For fast state flags.
- _Vector Databases (FAISS, Chroma, Pinecone):_ For semantic similarity search over unstructured past episodes.

### Step 3: Retrieval

When the user starts a new session and submits a query, the system performs **selective retrieval**. It asks: _"Given this user prompt, what past memories are relevant right now?"_. It fetches a small, targeted subset of memories from storage.

### Step 4: Injection

**Critical Architectural Rule:** Long-Term Memory is **never** passed directly into model weights. Instead, retrieved LTM facts are **injected into the short-term context window** as system prompt instructions. The LLM processes them as input tokens \(x\) via In-Context Learning.

# 12. Challenges and Modern Tools for Memory Systems

### Key Engineering Challenges

1. **Memory Creation Difficulty:** Deciding automatically which conversational facts are worth remembering long-term vs. which are trivial noise is extremely hard.
2. **Real-Time Selective Retrieval:** Searching and returning exact relevant memories in milliseconds without introducing latency.
3. **Orchestration Complexity:** Managing multiple databases, vector stores, background extraction loops, and thread states simultaneously.

### Modern Managed Memory Libraries & Platforms

To reduce development effort, specialized memory management frameworks have emerged:

- **LangMem (by LangChain):** A library specifically designed to handle long-term memory extraction and injection within LangGraph agents.
- **Mem0 (MemZero):** A platform providing a dedicated memory layer for GenAI applications via simple API calls.
- **SuperMemory:** An open-source long-term memory engine built for managing user memory profiles across applications.

---

# 13. The Future of Memory in LLMs

Currently, memory must be engineered around stateless models. However, cutting-edge AI research is exploring **architectures with intrinsic memory**.

- **Google's Titans + Mirage Architecture:** Recent research exploring new neural network layers that allow models to maintain an internal, continuously updating memory state natively within their weights during inference, potentially eliminating the need for complex external memory pipelines.

# 14. Final Revision Section

### Key Takeaways

- **Statelessness:** LLMs at inference are mathematical functions \(y = f(x, \theta)\) with frozen parameters.
- **Short-Term Memory:** Implemented by appending conversation history to input tokens \(x\) inside a thread-scoped buffer.
- **LTM Solution:** Long-Term Memory extracts selective facts across sessions and injects them back into short-term prompts.
- **LTM Triad:** Episodic (events), Semantic (facts), and Procedural (rules/workflows).

### Important Terminology

- **Parametric Knowledge (\(\theta\)):** Knowledge baked into model weights during pre-training.
- **In-Context Learning (ICL):** The model's ability to extract answers from text provided inside the prompt \(x\).
- **Context Window:** The token capacity an LLM can read and process at one time.
- **Thread Scoping:** Restricting short-term memory to a single isolated conversation session.
- **Memory Injection:** The process of inserting retrieved LTM facts into the current prompt's context window.

### Common Mistakes & Misconceptions

- _Misconception:_ "When an LLM learns my name in chat, it updates its internal model weights." \(\rightarrow\) **False:** The model weights \(\theta\) remain frozen; your name is simply passed back in prompt \(x\) on every turn.
- _Misconception:_ "Long-Term Memory replaces Short-Term Memory." \(\rightarrow\) **False:** LTM feeds _into_ STM. LTM facts are retrieved and injected into the prompt context window.

# Complete Python Implementation

Below is a complete Python script demonstrating:

1. Stateless LLM invocation vs. Stateful Short-Term Memory.
2. Thread persistence using a local database pattern.
3. Context trimming and summarization logic.
4. A conceptual Long-Term Memory extraction and prompt-injection workflow.

```
import os
from typing import List, Dict, Any
from dotenv import load_dotenv
from langchain_openai import ChatOpenAI
from langchain_core.messages import HumanMessage, AIMessage, SystemMessage

# Load environment variables
load_dotenv()

# =====================================================================
# 1. STATELESS VS SHORT-TERM MEMORY DEMO
# =====================================================================

model = ChatOpenAI(model="gpt-4o-mini", temperature=0)

def demonstrate_statelessness():
    print("--- 1. DEMONSTRATING STATELESSNESS ---")
    # Call 1
    res1 = model.invoke([HumanMessage(content="My name is Nitish")])
    print("Call 1 Output:", res1.content)

    # Call 2 (Stateless - forgets Call 1)
    res2 = model.invoke([HumanMessage(content="What is my name?")])
    print("Call 2 Output (No Memory):", res2.content)
    print("\n")

def demonstrate_short_term_memory():
    print("--- 2. DEMONSTRATING SHORT-TERM MEMORY (BUFFER) ---")
    conversation_buffer = []

    # Turn 1
    user_input_1 = "My name is Nitish and I am an AI instructor."
    conversation_buffer.append(HumanMessage(content=user_input_1))

    ai_response_1 = model.invoke(conversation_buffer)
    conversation_buffer.append(ai_response_1)
    print("AI Response 1:", ai_response_1.content)

    # Turn 2 (Passing full history back into prompt)
    user_input_2 = "What is my profession and name?"
    conversation_buffer.append(HumanMessage(content=user_input_2))

    ai_response_2 = model.invoke(conversation_buffer)
    conversation_buffer.append(ai_response_2)
    print("AI Response 2 (With STM):", ai_response_2.content)
    print("\n")

# =====================================================================
# 3. CONTEXT TRIMMING & LONG-TERM MEMORY INJECTION DEMO
# =====================================================================

class UserLongTermMemoryStore:
    """Simulates a database holding Semantic & Procedural Long-Term Memory."""
    def __init__(self):
        self.user_facts = {
            "name": "Nitish",
            "preferred_language": "Python",
            "disliked_languages": ["Java", "C++"],
            "coding_rules": "Always use SQL window functions instead of subqueries."
        }

    def retrieve_relevant_facts(self, query: str) -> str:
        """Simulates selective semantic search over memory store."""
        facts = []
        if "code" in query.lower() or "sql" in query.lower() or "python" in query.lower():
            facts.append(f"Preferred Language: {self.user_facts['preferred_language']}")
            facts.append(f"Coding Style Rule: {self.user_facts['coding_rules']}")
        return "\n".join(facts)

def run_ltm_injected_session():
    print("--- 3. LONG-TERM MEMORY INJECTION IN NEW THREAD ---")
    ltm_db = UserLongTermMemoryStore()

    # New Thread / Conversation Session (User starts fresh chat)
    user_query = "Write a query to get top 5 customers from orders table."

    # Step 1: Retrieve LTM facts relevant to user query
    retrieved_memory = ltm_db.retrieve_relevant_facts(user_query)

    # Step 2: Inject LTM into System Prompt (Short-Term Context Window)
    system_prompt = f"""
    You are an expert AI Assistant.

    [USER LONG-TERM MEMORY INJECTED]:
    {retrieved_memory}

    Follow the user's preferred coding rules strictly.
    """

    messages = [
        SystemMessage(content=system_prompt),
        HumanMessage(content=user_query)
    ]

    # Step 3: Invoke LLM
    response = model.invoke(messages)
    print("User Query:", user_query)
    print("System Response (Personalized via LTM Injection):\n", response.content)

if __name__ == "__main__":
    demonstrate_statelessness()
    demonstrate_short_term_memory()
    run_ltm_injected_session()
```
