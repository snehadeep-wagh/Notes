
# 1. Introduction to Parallel Workflows

### **Detailed Explanation**

A **Parallel Workflow** is an architectural pattern where multiple tasks (nodes) are executed at the same time because they do not depend on each other's outputs. Once these independent tasks are complete, their results are typically funneled into an "Aggregator" or "Summary" node to be merged.

### **Key Concepts**

- **Independent Execution:** Nodes that can run without waiting for results from siblings.
- **Fan-out / Fan-in:** The "fan-out" is when one node (like `START`) triggers multiple parallel nodes. The "fan-in" is when those parallel nodes converge into a single downstream node.
- **Efficiency:** Parallelism significantly reduces the total runtime of a graph compared to sequential execution, especially when dealing with slow LLM API calls.

### **Why It Matters**

- **Speed:** Running three LLM calls simultaneously is much faster than running them one after another.
- **Specialization:** Different nodes can be optimized for specific sub-tasks (e.g., one for grammar, one for logic).
- **Reduced Context Window Issues:** Instead of asking one LLM to do everything (which might lead to "forgetting" instructions), you give specialized instructions to specialized parallel nodes.

# 2. Example 1: Non-LLM Parallel Workflow (Cricket Stats)

This example provides the foundational syntax for parallelization by calculating cricket metrics like Strike Rate and Boundary Percentages simultaneously.

### **Workflow Structure**

The input consists of basic data points: Runs, Balls, Fours, and Sixes. Three nodes calculate specific stats in parallel, and a final node summarizes them.

```
graph TD
    START((START)) --> A[Calculate Strike Rate]
    START --> B[Calculate Boundary %]
    START --> C[Calculate Balls per Boundary]
    A --> D[Summary Node]
    B --> D
    C --> D
    D --> END((END))
```

### **The "Invalid Update" Conflict**

When building parallel workflows, a common error occurs: `InvalidUpdateError`.

- **The Cause:** If parallel nodes return the **entire state**, LangGraph receives multiple conflicting updates for the same keys (like `runs` or `balls`), even if those values didn't change.
- **The Solution: Partial State Updates.** Nodes must only return a dictionary containing the specific keys they calculated.

### **State Table: Cricket Workflow**

|Key|Type|Purpose|
|:--|:--|:--|
|`runs`|`int`|Total runs (Input)|
|`balls`|`int`|Total balls (Input)|
|`force`|`int`|Number of fours (Input)|
|`sixes`|`int`|Number of sixes (Input)|
|`strike_rate`|`float`|Calculated Strike Rate|
|`summary`|`str`|Final concatenated string|

### **Complete Python Implementation**

```
from typing import TypedDict
from langgraph.graph import StateGraph, START, END

# 1. Define State
class BatsmanState(TypedDict):
    runs: int
    balls: int
    force: int
    sixes: int
    strike_rate: float
    bpb: float # Balls per Boundary
    boundary_percent: float
    summary: str

# 2. Define Nodes with Partial Updates
def calculate_strike_rate(state: BatsmanState):
    sr = (state["runs"] / state["balls"]) * 100
    return {"strike_rate": sr} # Partial Update

def calculate_bpb(state: BatsmanState):
    total_boundaries = state["force"] + state["sixes"]
    bpb = state["balls"] / total_boundaries
    return {"bpb": bpb}

def calculate_boundary_percent(state: BatsmanState):
    boundary_runs = (state["force"] * 4) + (state["sixes"] * 6)
    percent = (boundary_runs / state["runs"]) * 100
    return {"boundary_percent": percent}

def summary_node(state: BatsmanState):
    summary = f"SR: {state['strike_rate']}, BPB: {state['bpb']}"
    return {"summary": summary}

# 3. Build Graph
builder = StateGraph(BatsmanState)
builder.add_node("sr_node", calculate_strike_rate)
builder.add_node("bpb_node", calculate_bpb)
builder.add_node("bp_node", calculate_boundary_percent)
builder.add_node("summary", summary_node)

# Parallel Fan-out
builder.add_edge(START, "sr_node")
builder.add_edge(START, "bpb_node")
builder.add_edge(START, "bp_node")

# Fan-in to Aggregator
builder.add_edge("sr_node", "summary")
builder.add_edge("bpb_node", "summary")
builder.add_edge("bp_node", "summary")
builder.add_edge("summary", END)

workflow = builder.compile()
```

# 3. Example 2: LLM-Based UPSC Essay Evaluator

This complex example integrates three advanced concepts: **Parallelism**, **Structured Output**, and **Reducers**.

### **The Three-Pillar Strategy**

1. **Parallelism:** Three LLM calls evaluate "Clarity of Thought," "Depth of Analysis," and "Language" simultaneously.
2. **Structured Output:** Uses Pydantic to force the LLM to return a consistent JSON format (Text Feedback + Score 0-10).
3. **Reducers:** Uses `operator.add` to merge scores from parallel nodes into a single list without overwriting.

### **Detailed Notes: Reducers & Annotated**

By default, LangGraph replaces values in the state. To **append** values (like merging scores into a list from parallel nodes), we use the `Annotated` type with a reducer function like `operator.add`.

```
from typing import Annotated, List
import operator

# The Annotated type tells LangGraph: "Don't replace this list,
# use operator.add to merge new values into it".
individual_scores = Annotated[List[int], operator.add]
```

### **State Table: UPSC Evaluator**

|Key|Type|Purpose|
|:--|:--|:--|
|`essay_text`|`str`|The user's essay|
|`clarity_feedback`|`str`|Feedback on logic/thought|
|`individual_scores`|`Annotated[list, add]`|Collection of scores (0-10) from all 3 nodes|
|`average_score`|`float`|Final calculated average|

### **Complete Python Code**

```
from pydantic import BaseModel, Field
from langchain_openai import ChatOpenAI

# Step 1: Structured Output Schema
class EvaluationSchema(BaseModel):
    feedback: str = Field(description="Detailed textual feedback")
    score: int = Field(description="Score from 0 to 10")

model = ChatOpenAI(model="gpt-4o-mini")
structured_llm = model.with_structured_output(EvaluationSchema)

# Step 2: Nodes
def evaluate_language(state: UPSCState):
    prompt = f"Evaluate language quality: {state['essay_text']}"
    res = structured_llm.invoke(prompt)
    return {
        "language_feedback": res.feedback,
        "individual_scores": [res.score] # Returns as list for reducer
    }

# Step 3: Aggregator Node
def final_eval_node(state: UPSCState):
    avg = sum(state["individual_scores"]) / len(state["individual_scores"])
    return {"average_score": avg}
```

# Final Revision Section

### **Key Takeaways**

- **Partial Updates are Mandatory:** Parallel nodes must only return the keys they intend to update to avoid `InvalidUpdateError`.
- **Reducers enable Merging:** Use `Annotated` with `operator.add` when you need parallel nodes to contribute to a shared list or counter.
- **Structured Output ensures Reliability:** Forcing LLMs into a schema (Pydantic) makes downstream processing (like calculating averages) possible without parsing errors.

### **Important Terminology**

- **Fan-out:** One source node pointing to multiple parallel nodes.
- **Fan-in:** Multiple parallel nodes merging back into one aggregator node.
- **Structured Output:** A technique to ensure LLM responses follow a strict JSON schema.
- **operator.add:** A standard Python function used as a reducer to combine lists or numbers.
