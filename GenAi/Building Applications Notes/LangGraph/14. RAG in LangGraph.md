### **4. Why RAG? (The Three Primary Motivations)**

#### **Detailed Notes**

Retrieval-Augmented Generation addresses three fundamental limitations of Large Language Models:

```
mindmap
  root((Why RAG?))
    Outdated Knowledge
      Knowledge Cutoff Date
      Cannot know post-training events
      Web Search as real-time RAG
    Privacy & Private Data
      Internal company financial reports
      Personal expense sheets
      Private research PDFs
    Hallucination Reduction
      Prevents fabricated facts & broken links
      Grounds LLM in provided context
      Strict prompt boundaries
```

#### **1. Outdated Knowledge (Knowledge Cutoff Dates)**

LLMs are trained on fixed datasets up to a specific completion date (the **Knowledge Cutoff Date**). For example, if a model's training completed on August 31st, it cannot answer queries about events occurring after that date without external retrieval. Web search tools used by commercial assistants are simply real-time web-based RAG pipelines.

#### **2. Privacy and Proprietary Data**

LLMs are trained on public web data and have no access to personal or enterprise data. RAG allows organizations and individuals to connect private documents (e.g., financial audit reports, private e-books, personal spreadsheets) to an LLM without exposing those files to public training sets.

#### **3. Hallucination Reduction**

When asked questions outside their parametric knowledge, LLMs tend to generate plausible-sounding but false information with high confidence (e.g., fabricating fake paper titles or returning 404 links). RAG forces the model to answer strictly based on the retrieved document context, anchoring its responses in verified facts.

### **5. RAG Principle: In-Context Learning & Context Filtering**

#### **Detailed Notes**

At its core, RAG relies on **In-Context Learning**. Rather than modifying the model's weights (fine-tuning), we append relevant background context directly into the prompt alongside the user's question.

#### **The Naive Pasting Problem & Token Limits**

If a user wants to ask questions about a 200-page book or a massive codebase containing thousands of files, pasting the entire raw document into the prompt fails:

- It exceeds the model's **Context Window Limit** (maximum token capacity).
- It increases API costs and processing latency.

#### **The Solution: Context Filtering**

RAG acts as a **smart context filter**. Instead of passing all 200 pages, the retriever extracts only the **4 to 6 pages** that are semantically relevant to the user's query and inserts only those chunks into the prompt.

|Strategy|Mechanism|Context Window Risk|Accuracy & Cost|
|:--|:--|:--|:--|
|**Naive Full Pasting**|Appends entire raw files to prompt.|Extremely High (Exceeds token limits).|Low accuracy, high latency, expensive.|
|**RAG Context Filtering**|Retrieves top-k semantic chunks.|Very Low (Fits comfortably in window).|High accuracy, fast response, cost-effective.|

### **6. High-Level RAG Architecture**

#### **Detailed Notes**

A production RAG pipeline consists of two primary operational phases: **The Indexing Pipeline** (offline setup) and **The Retrieval Pipeline** (runtime execution).

```
flowchart TD
    subgraph Indexing Pipeline
        A[Raw Document / PDF] --> B[PyPDFLoader: Load Data]
        B --> C[RecursiveTextSplitter: Create Chunks]
        C --> D[OpenAIEmbeddings: Generate Vectors]
        D --> E[(FAISS Vector Store)]
    end

    subgraph Retrieval Pipeline
        F[User Query] --> G[Retriever: Similarity Search]
        E <-->|Vector Comparison| G
        G --> H[Extract Page Contents & Metadata]
        H --> I[Prompt Assembly: Context + Query]
        I --> J[LLM: gpt-4o-mini]
        J --> K[Grounded Output]
    end
```

#### **The Step-by-Step Architecture**

1. **Document Ingestion:** Raw documents (PDFs, text files) are loaded into memory.
2. **Chunk Splitting:** Documents are split into smaller text blocks (chunks) using overlapping windows to retain semantic continuity between boundaries.
3. **Embedding Generation:** Text chunks are passed through an embedding model (e.g., `text-embedding-3-small`) to produce dense numerical vectors capturing their semantic meaning.
4. **Vector Storage:** Vectors and their corresponding text contents and metadata are saved in a specialized vector database (e.g., FAISS or Chroma).
5. **Semantic Search & Retrieval:** When a query arrives, the retriever converts the query into a vector, calculates cosine similarity against the database, and returns the top-k most similar chunks.
6. **Prompt Assembly & Generation:** The retrieved text and metadata are combined with the original query in a prompt template and sent to the LLM to generate the final response.

### **7. Implementation Setup & Indexing Pipeline**

#### **Detailed Notes**

In the standalone implementation (`rag.ipynb`), we build the indexing pipeline step-by-step using LangChain components:

- **PDF Loading:** `PyPDFLoader` parses the target document into a list of document objects.
- **Text Splitting:** `RecursiveCharacterTextSplitter` breaks the loaded text into manageable chunks. It uses parameter settings like `chunk_size` (e.g., 1000 characters) and `chunk_overlap` (e.g., 200 characters) to preserve context across chunk boundaries.
- **Embedding Model:** `OpenAIEmbeddings(model="text-embedding-3-small")` converts each text chunk into a floating-point vector array.
- **Vector Store Initialization:** `FAISS.from_documents(chunks, embeddings)` builds an in-memory vector index.
- **Retriever Creation:** `vector_store.as_retriever(search_type="similarity", search_kwargs={"k": 4})` converts the index into a search interface that returns the top 4 most relevant chunks for any query.

Calling `retriever.invoke("What is a decision tree?")` demonstrates how the retrieval layer extracts matches from the FAISS database:

### **9. Wrapping RAG as a LangGraph Tool**

#### **Detailed Notes**

In an agentic architecture, RAG should not be a rigid, hardcoded step. Instead, we wrap the retriever inside a custom Python function decorated with `@tool`. This turns RAG into a dynamic tool that the LLM can choose to invoke whenever it detects a document-related query.

```
graph TD
    START((START)) --> ChatNode[Chat Node: LLM with Bound Tools]
    ChatNode --> Router{tools_condition}
    Router -- "User asked about PDF" --> ToolNode[ToolNode: Executing rag_tool]
    Router -- "General Query" --> END((END))
    ToolNode -->|Return Retracted Context & Metadata| ChatNode
```

#### **Key Graph Architecture Design**

- **Tool Registration:** The `rag_tool` function is placed inside a tools array and bound to the LLM using `model.bind_tools([rag_tool])`.
- **`ChatNode`:** Invokes the tool-bound model to process conversation history and user prompts.
- **`ToolNode`:** Uses LangGraph's pre-built `ToolNode` class to execute `rag_tool` when requested by the LLM.
- **Reasoning Loop:** The output of `ToolNode` feeds back into `ChatNode`. This allows the LLM to inspect the retrieved text and synthesize a polished answer for the user.

#### **Detailed Notes**

Running document-grounded queries takes roughly **8 to 9 seconds** per run due to similarity search, prompt assembly, and model generation.

To inspect the execution flow step-by-step, we use **LangSmith** tracing:

```
sequenceDiagram
    participant User as User / Streamlit UI
    participant Chat as ChatNode (LLM)
    participant Tool as ToolNode (rag_tool)
    participant DB as FAISS Vector DB

    User->>Chat: "Explain how to split a node in a decision tree"
    Note over Chat: Step 1: LLM inspects prompt & tools
    Chat->>Tool: Emit tool_calls -> rag_tool(query="split node decision tree")
```

1. **Step 1 (`ChatNode`):** Receives the user prompt: _"Explain how to split a node in a decision tree"_. The model decides it needs external context and emits a `tool_call` targeting `rag_tool` with the extracted search query.
2. **Step 2 (`ToolNode`):** Executes `rag_tool`. The function queries the FAISS index, retrieves the top 4 matching document chunks, extracts their text and metadata, and returns a `ToolMessage`.
3. **Step 3 (`ChatNode` Re-entry):** The LLM receives the original query along with the newly retrieved document context. It synthesizes a concise response grounded in the retrieved text and routes the workflow to `END`.

# Final Revision Section

### **Key Takeaways**

- **In-Context Learning:** RAG works by supplying relevant external text chunks inside the LLM prompt rather than fine-tuning model weights.
- **Tool-Based RAG:** Wrapping retrievers inside a `@tool` decorator allows agentic models to decide _when_ to search uploaded documents and _when_ to use other capabilities.
- **Overlapping Chunks:** Text splitters use overlapping character windows to ensure context is preserved across chunk splits.
- **Trace Visibility:** LangSmith allows developers to inspect the exact document chunks retrieved during agent execution, making it easier to debug hallucinations.

### **Important Terminology**

- **RAG (Retrieval-Augmented Generation):** A framework that enhances LLM responses by retrieving relevant data from external knowledge sources.
- **Vector Store (FAISS):** A database optimized for storing numerical vector embeddings and performing similarity searches.
- **`RecursiveCharacterTextSplitter`:** A LangChain utility that splits text into chunks based on character boundaries while preserving context.
- **`ToolMessage`:** A message payload containing data returned by an executed tool.

# Complete Python Implementation

Below is the complete, production-grade Python code split into the **Backend Module** (`langgraph_rag_backend.py`) and the **Frontend Streamlit Interface** (`streamlit_rag_frontend.py`).

### **File 1: `langgraph_rag_backend.py` (Backend Engine)**

```
import os
import sqlite3
from typing import List, Dict, Any
from dotenv import load_dotenv

from langchain_openai import ChatOpenAI, OpenAIEmbeddings
from langchain_community.document_loaders import PyPDFLoader
from langchain_text_splitters import RecursiveCharacterTextSplitter
from langchain_community.vectorstores import FAISS
from langchain_core.tools import tool
from langchain_community.tools import DuckDuckGoSearchRun
from langchain_core.messages import HumanMessage, AIMessage, SystemMessage

from langgraph.graph import StateGraph, START, END, MessagesState
from langgraph.checkpoint.sqlite import SqliteSaver
from langgraph.prebuilt import ToolNode, tools_condition

# Load environment API keys
load_dotenv()

# =====================================================================
# 1. GLOBAL STATE & VECTOR STORE HOLDER
# =====================================================================
# Global variable to hold our dynamic FAISS retriever once a PDF is uploaded
global_retriever = None

# Initialize persistent SQLite database checkpointer
conn = sqlite3.connect("rag_chatbot.db", check_same_thread=False)
memory_saver = SqliteSaver(conn)

# =====================================================================
# 2. DOCUMENT INGESTION PIPELINE
# =====================================================================
def ingest_pdf(file_path: str):
    """
    Loads a PDF document, splits it into overlapping chunks,
    generates vector embeddings, and builds a FAISS retriever.
    """
    global global_retriever

    # Step A: Load PDF
    loader = PyPDFLoader(file_path)
    documents = loader.load()

    # Step B: Recursive Text Splitting
    text_splitter = RecursiveCharacterTextSplitter(
        chunk_size=1000,
        chunk_overlap=200
    )
    chunks = text_splitter.split_documents(documents)

    # Step C: Generate Embeddings and Store in FAISS
    embeddings = OpenAIEmbeddings(model="text-embedding-3-small")
    vector_store = FAISS.from_documents(chunks, embeddings)

    # Step D: Instantiate Similarity Retriever (Top-4 matches)
    global_retriever = vector_store.as_retriever(
        search_type="similarity",
        search_kwargs={"k": 4}
    )
    return True

# =====================================================================
# 3. DEFINE TOOLS (RAG + MULTI-UTILITY)
# =====================================================================
@tool
def rag_tool(query: str) -> Dict[str, Any]:
    """
    Retrieves information from uploaded PDF documents.
    Always use this tool when the user asks questions about uploaded files or document content.
    """
    global global_retriever
    if global_retriever is None:
        return {"error": "No document has been uploaded or indexed yet."}

    # Execute vector similarity search
    docs = global_retriever.invoke(query)

    # Extract page contents and metadata
    page_contents = [doc.page_content for doc in docs]
    metadatas = [doc.metadata for doc in docs]

    return {
        "query": query,
        "retrieved_context": page_contents,
        "metadata": metadatas
    }

# Web Search Tool
search_tool = DuckDuckGoSearchRun()

# Calculator Tool
@tool
def calculator(first_number: float, second_number: float, operation: str) -> str:
    """Perform basic math calculations: 'add', 'subtract', 'multiply', 'divide'."""
    if operation == "add":
        return str(first_number + second_number)
    elif operation == "subtract":
        return str(first_number - second_number)
    elif operation == "multiply":
        return str(first_number * second_number)
    elif operation == "divide":
        return str(first_number / second_number) if second_number != 0 else "Division by zero error."
    return "Invalid operation."

# Stock Price Tool
@tool
def get_stock_price(ticker: str) -> str:
    """Fetches the stock price for a given ticker symbol (e.g. AAPL, GOOG)."""
    stock_data = {"AAPL": "180.25 USD", "GOOG": "154.10 USD", "TSLA": "220.50 USD"}
    return f"Current stock price for {ticker.upper()} is {stock_data.get(ticker.upper(), '150.00 USD')}."

# Consolidate all tools into an array
tools_list = [rag_tool, search_tool, calculator, get_stock_price]

# =====================================================================
# 4. LANGGRAPH AGENT ORCHESTRATION
# =====================================================================
model = ChatOpenAI(model="gpt-4o-mini", temperature=0)
model_with_tools = model.bind_tools(tools_list)

def chat_node(state: MessagesState):
    """Processes messages using our tool-bound model."""
    response = model_with_tools.invoke(state["messages"])
    return {"messages": [response]}

# Create pre-built ToolNode
tool_executor = ToolNode(tools_list)

# Build StateGraph
builder = StateGraph(MessagesState)
builder.add_node("chatbot", chat_node)
builder.add_node("tools", tool_executor)

builder.add_edge(START, "chatbot")
builder.add_conditional_edges(
    "chatbot",
    tools_condition,
    {
        "tools": "tools",
        "__end__": END
    }
)
builder.add_edge("tools", "chatbot")

# Compile graph with persistent database memory
rag_agent_graph = builder.compile(checkpointer=memory_saver)

# =====================================================================
# 5. UTILITY TO FETCH HISTORIC THREADS
# =====================================================================
def retrieve_all_threads() -> list:
    """Queries SQLite database to return all unique thread IDs."""
    all_threads = set()
    for checkpoint in memory_saver.list(None):
        thread_id = checkpoint.config["configurable"]["thread_id"]
        all_threads.add(thread_id)
    return list(all_threads)
```
