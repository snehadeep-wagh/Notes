
### **1. Tool Binding**

**Definition:** Tool binding is the registration process where you connect your tools to a Large Language Model (LLM).

- **How it Works:** By binding a tool, the LLM receives a JSON schema containing the tool's **name**, **description** (from the docstring), and **input arguments**. This allows the LLM to know exactly what capabilities it has and how to format requests for them.
- **Key Constraint:** Not all models support tool binding; only specific models designed for function calling can utilize this feature.

**Python Code Example:**

```
from langchain_openai import ChatOpenAI
from langchain_core.tools import tool

# 1. Define a tool
@tool
def multiply(a: int, b: int) -> int:
    """Multiply two numbers and return the product."""
    return a * b

# 2. Initialize LLM
llm = ChatOpenAI(model="gpt-4o")

# 3. Binding: Register the tool with the LLM
llm_with_tools = llm.bind_tools([multiply])
```

---

### **2. Tool Calling**

**Definition:** This is the "decision-making" phase where the LLM determines that a specific tool is required to answer a user's query.

- **The Output:** Instead of a regular text response, the LLM generates a structured **Tool Call**.
- **Crucial Distinction:** The LLM **does not run the tool**. It only suggests the tool name and the arguments required to run it. Execution is left to the programmer or the framework for security and control.

**Conceptual Workflow Diagram:**

1. **User:** "What is 8 times 7?"
2. **LLM Reasoning:** "I have a `multiply` tool. I need to use it."
3. **LLM Output:** An `AIMessage` containing `tool_calls=[{'name': 'multiply', 'args': {'a': 8, 'b': 7}}]`.

---

### **3. Tool Execution**

**Definition:** The practical step where the Python function (the tool) is actually invoked using the arguments provided by the LLM.

- **Mechanism:** The programmer takes the `tool_calls` from the LLM response and passes them into the tool's `.invoke()` method.
- **ToolMessage:** Once executed, the result is wrapped in a `ToolMessage`. This message, along with the conversation history, is sent back to the LLM so it can generate a final human-readable answer.

**Tool Workflow Table:** | Phase | Agent | Action | Result | | :--- | :--- | :--- | :--- | | **Binding** | Programmer | Registers tools to LLM | LLM knows its "skills" | | **Calling** | LLM | Suggests tool + arguments | Structured JSON output | | **Execution** | Programmer | Runs the Python function | `ToolMessage` (Result) |

### **InjectedToolArg**

An **Injected Tool Argument** is a special parameter in a LangChain tool that the LLM is explicitly told **not** to fill. Instead, the developer or the system provides this value manually during the **Tool Execution** phase.

**Why use Injected Tool Arguments?**

- **Prevent Hallucinations:** Without injection, an LLM might try to "guess" a value (like a real-time exchange rate) using its outdated training data rather than waiting for a live result from another tool.
- **Chain Tool Results:** It allows you to take the output of one tool (e.g., a live conversion factor) and feed it directly into a second tool (e.g., a calculator).
- **Security & Logic:** It ensures critical values are handled by your code's logic rather than the LLM's unpredictable reasoning.

**How it Works in Practice**

In the currency conversion example, the LLM is given two tools: `get_conversion_factor` and `convert_value`.

1. You mark the `conversion_rate` in the second tool as an **InjectedToolArg**.
2. When the user asks to convert money, the LLM suggests calling both tools but **leaves the rate blank** for the second one.
3. You (the programmer) run the first tool to get the live rate.
4. You then manually insert that rate into the arguments dictionary of the second tool call before invoking it.

```
from typing import Annotated
from langchain_core.tools import InjectedToolArg

@tool
def convert_value(amount: int, 
                  rate: Annotated[float, InjectedToolArg]): # LLM ignores 'rate'
    return amount * rate
```

### **4. Real-World Example: Currency Conversion Tool**

Standard LLMs lack real-time data like current exchange rates. This application creates a tool to fetch live data from an API and perform calculations.

**A. Tool Definition**

We define two tools: one to fetch the rate and one to calculate the final value. We use **Injected Tool Arguments** to ensure the LLM doesn't try to "guess" values (like the rate) that the developer will provide later.

```
import json
import requests
from typing import Annotated
from langchain_core.tools import tool, InjectedToolArg

@tool
def get_conversion_factor(base_currency: str, target_currency: str) -> float:
    """Fetches the current conversion factor between two currencies."""
    url = f"https://v6.exchangerate-api.com/v6/YOUR_KEY/pair/{base_currency}/{target_currency}"
    response = requests.get(url)
    return response.json()['conversion_rate']

@tool
def convert_value(base_value: int, 
                  conversion_rate: Annotated[float, InjectedToolArg]) -> float:
    """Calculates target currency value using a base value and a rate."""
    return base_value * conversion_rate
```

**B. Orchestration Logic**

The code must handle a "loop" of tool calls, especially when one tool depends on the result of another.

```
# Assuming LLM is bound to [get_conversion_factor, convert_value]
query = "Convert 10 USD to INR"
messages = [HumanMessage(content=query)]
ai_msg = llm_with_tools.invoke(messages)

# Manual Execution Loop (Simplified)
for tool_call in ai_msg.tool_calls:
    if tool_call['name'] == 'get_conversion_factor':
        # 1. Run first tool
        rate = get_conversion_factor.invoke(tool_call['args'])
    
    if tool_call['name'] == 'convert_value':
        # 2. Inject result from Tool 1 into Tool 2
        tool_call['args']['conversion_rate'] = rate
        result = convert_value.invoke(tool_call['args'])

# Final Answer
messages.extend([ai_msg, ToolMessage(content=str(result), tool_call_id=...)])
final_response = llm_with_tools.invoke(messages)
print(final_response.content) # "10 USD is roughly 853 INR."
```

**C. Why isn't this an "Agent"?**

Even though it uses tools, this specific script is **not** an autonomous agent because the programmer is manually managing the loop and logic. An actual AI Agent would decide which tool to call first and manage the sequence independently without the developer writing "if-else" logic for every tool call.
